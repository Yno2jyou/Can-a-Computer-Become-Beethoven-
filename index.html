アップロード済みの既存HTMLを直接改修し、現在の「人間が最初に5音を入力し、その5音を起点としてコンピューターが長時間かけて旋律を生成・進化させていく」というコンセプトを維持したまま、**世に出ている一般的な楽曲と比較しても遜色のない、記憶性・歌唱性・展開性・美しさを持つメロディを自律的に発見できる作曲システム**へ大幅に進化させること。 既存のUI、キーボード、オーディオエンジン、リアルタイム生成、テーマ記憶、変奏、転調、テンポ・ダイナミクス、対旋律、和声、進化フェーズなど、現在すでに成立している機能は原則として維持する。単なるランダム音列生成への回帰は禁止。外部AI API、生成AI API、クラウドサービス、外部音楽生成APIには依存せず、**JavaScriptだけで完全にローカル実行できる自律的なアルゴリズム**として実装する。 ### 1. 最重要目標 現在のシステムは、音程・音域・順次進行・跳躍・リズム・反復などを評価して「音楽的にもっともらしい旋律」を選択している。しかし、それだけでは「きれいな音の羅列」から脱却できない。 改修後は、単に各音が美しいかどうかではなく、 「記憶できる」 「次を予測したくなる」 「予想通りなのに少し意外」 「フレーズ全体に方向性がある」 「緊張が生まれ、後で解放される」 「同じモチーフが別の姿で戻ってくる」 「一度聴いただけでも輪郭を覚えられる」 「最高潮となる音が明確に存在する」 「終止したときに、それまでの流れが回収されたように感じる」 という、**旋律全体の心理的・構造的な性質**を評価できるようにする。 ### 2. 現在のモチーフ進化システムを中核として残す 既存のテーマ生成、モチーフ変異、反行、逆行、断片化、リズム変換、音程変換、記憶からのテーマ再利用、対旋律からの新テーマ発見などは維持する。 特に、人間が最初に弾いた5音を単なる初期値ではなく、**旋律の遺伝的DNA**として扱う。 最初の5音から、 ・原型 ・反行 ・逆行 ・拡大 ・縮小 ・断片化 ・リズム変換 ・音域変更 ・オクターブ変更 ・終止音変更 ・装飾 ・対旋律化 ・和声変更 ・別テンポ化 などを生成し、最終的な旋律が大きく変化しても「最初の5音から生まれた」という痕跡をどこかに残す。 ### 3. 「期待」と「裏切り」を評価する新しい旋律評価関数を実装する 新しい `melodicExpectationScore()` を実装する。 各フレーズについて、それまでの音列から「次に来る可能性が高い音」を内部的に予測し、実際の次音との差を評価する。 ただし、予測通りなら常に高得点、予想外なら低得点という単純な評価にはしない。 理想的な旋律は、 「予測可能性」と「意外性」 が共存するものとして扱う。 目標は概念的に、 予測可能性 約70% 意外性 約30% 程度のバランス。 完全に予想通りの旋律は退屈なので減点し、完全にランダムな旋律も音楽的文脈を失うため減点する。 「ほとんど予想できるのに、重要な瞬間だけ予想を裏切る」旋律を高く評価する。 特に、 ・フレーズ終盤の予想外の音 ・跳躍後の予想外の着地点 ・一度確立されたパターンからの逸脱 ・終止直前の回避 ・期待を引き延ばした後の解決 などを評価する。 ### 4. 「フレーズの物語性」を評価する 各旋律を単なる音符列ではなく、一つの小さな物語として扱う。 各フレーズに、 `DEPARTURE` → `RISE` → `TENSION` → `CLIMAX` → `RELEASE` という内部的な構造を持たせる。 例えば8小節なら、 1〜2小節：導入 3〜4小節：上昇・展開 5小節：クライマックス 6小節：余韻・緊張 7〜8小節：解放・着地 のような構造を候補として生成する。 ただし毎回同じ構造に固定せず、クライマックス位置、音域、リズム密度、休符、和声、テンポを変化させる。 「どこへ向かっているのかわからない旋律」は減点する。 ### 5. メロディの「頂点」を明確にする 各フレーズに、一つまたは少数の重要な高点を設定する。 現在の最高音評価をさらに高度化し、 ・頂点の位置 ・頂点までの上昇過程 ・頂点直前の音程 ・頂点の長さ ・頂点のリズム的位置 ・頂点のvelocity ・頂点上で鳴る和音 ・頂点後の下降・解放 を連動させる。 単に一番高い音を置くのではなく、**「そこへ向かって旋律が進んできた」と感じられる頂点**を作る。 頂点が序盤にある場合、頂点が何度も現れる場合、最大音域まで無意味に飛ぶ場合などは必要に応じて減点する。 ### 6. 「反復」と「変奏」を高度化する 既存のA / A' / B / A''的な構造をさらに強化する。 重要なのは完全コピーではなく、 **「同じ旋律だと認識できるが、以前とは違う」** という状態。 モチーフの変奏時には、 ・音高 ・リズム ・音域 ・開始位置 ・終止音 ・方向 ・装飾 ・和声 ・休符 ・アクセント を独立したパラメータとして変化させる。 ただし変化させすぎて元のモチーフとの関係が消えた場合は減点する。 「T → T' → T'' → B → T'''」 のように、時間経過によってモチーフが変化しながら帰還する構造を作る。 ### 7. 「記憶性」を独立した評価項目にする 旋律が一度聴いただけで覚えられそうかを機械的に推定する。 評価対象： ・短い特徴的な音程パターン ・特徴的なリズム ・反復 ・適度な単純性 ・適度な非対称性 ・明確な輪郭 ・特徴的な跳躍 ・同一モチーフの再登場 特に、単純すぎる旋律と複雑すぎる旋律の両方を減点する。 「覚えやすいが単純すぎない」という領域を高評価にする。 ### 8. 旋律全体を評価する階層型進化システムを実装する 現在の「候補を生成→scoreSegment()で最高候補を採用」という構造を発展させる。 一つのフレーズについて大量の候補を生成する。 概念的には、 100〜500候補生成 ↓ 第1次評価 ↓ 上位50候補 ↓ 第2次評価 ↓ 上位10候補 ↓ フレーズ全体の構造評価 ↓ 上位3〜5候補 ↓ 前後の旋律との接続評価 ↓ 和声との相互作用評価 ↓ 最終候補決定 という多段階選抜を行う。 CPU負荷を考慮し、実際の数値はブラウザ上でリアルタイムに動作できる範囲に自動調整する。 ### 9. 「最高点だけ」を採用しない 毎回スコア1位の旋律だけを選択すると、システムが保守的になり、似たような旋律ばかりになる。 そのため候補を、 ・BEST BEAUTY ・BEST MEMORY ・BEST SURPRISE ・BEST ORIGINALITY ・BEST HUMAN-LIKE など複数の観点から保存する。 その後、それらを次世代の親として交配・変異させる。 つまり、 「最も点数が高い旋律」 だけではなく、 「美しい旋律」 「記憶に残る旋律」 「奇妙だが魅力的な旋律」 「意外性のある旋律」 「人間が作ったような旋律」 を別々に保存し、次の世代で再結合する。 ### 10. 交配システムを追加する 上位候補同士から新しい旋律を作る。 例えば、 親Aの前半 + 親Bの後半 親Aのリズム + 親Bの音程 親Aの輪郭 + 親Bの終止 などを組み合わせる。 ただし単純なランダム結合ではなく、拍位置・フレーズ位置・モチーフ境界を考慮する。 さらに、 「Aのモチーフ + Bのリズム」 「Aの音域 + Bの終止」 「Aの頂点 + Bの下降」 などの部分的交配も可能にする。 ### 11. 「異常な候補」を意図的に生成する 全候補を美しいものだけに制限しない。 一定割合で、 ・大跳躍 ・半音進行 ・突然の休符 ・急激な音域移動 ・変拍子 ・極端な長音 ・予想外の終止 ・リズム崩壊 ・一時的な調外音 ・突然の速度変化 などを許容する。 ただし最終評価では、単なる無秩序は淘汰する。 重要なのは、 **「異常な候補の中から、意外にも美しいものを発見する」** こと。 現在の `evoBreak()` のようなleap / meter / chrom / tempo / silence / registerなどの破壊イベントは、単なる演出ではなく、**新しい旋律探索を生む探索アルゴリズムとして利用する。** ### 12. 対旋律から新しい主旋律を発見する 現在存在する「対旋律の断片から新しいテーマを発見する仕組み」をさらに強化する。 主旋律 ↓ 対旋律 ↓ 偶然生まれた特徴的な4〜6音 ↓ その断片を独立した候補として保存 ↓ 変奏 ↓ 新テーマ化 ↓ 主旋律として再登場 という自己発見ループを実装する。 これにより、コンピューター自身が「最初に作ったテーマとは別の、より魅力的なテーマ」を発見できるようにする。 ### 13. 人間の5音を「遺伝的記憶」として永続利用する 最初の5音は、生成開始時だけ使って終わりにしない。 システム内部に、 `ORIGINAL DNA` として保存する。 長時間の生成後も、 ・音程関係 ・リズム ・輪郭 ・音域 ・特徴的な跳躍 の一部が、どこかの世代で再登場する可能性を残す。 ただし露骨に毎回引用するのは禁止。 最初の5音が直接聴こえることもあれば、何十段階もの変奏を経て全く別の姿で現れることもあるようにする。 最終的な旋律から原型DNAへの類似度も内部的に計測する。 ### 14. 和声と旋律を相互依存させる 和声を後から付けるのではなく、 「この旋律だからこの和声が生まれる」 「この和声だからこの旋律が美しく聞こえる」 という双方向の関係を作る。 特に、 ・フレーズ頂点 ・緊張音 ・非和声音 ・解決音 ・終止 ・半終止 を和声と連動させる。 対旋律についても主旋律と衝突しないだけではなく、**主旋律をより美しく聴かせる役割**を評価する。 ### 15. 「音符単体」ではなく「時間的な流れ」を評価する fitnessは単純な音程加点の総和にしない。 最終的な総合評価は概念的に、 ```text Melody Score = 音程自然性 + リズム自然性 + 歌唱性 + 記憶性 + モチーフ性 + 反復性 + 変奏性 + 期待と意外性 + フレーズ構造 + 緊張と解放 + クライマックス + 終止感 + 和声適合性 + 独創性 + 文脈適合性 - 無意味な反復 - 過剰なジグザグ - 過剰な跳躍 - 無秩序 - 予測不能すぎる展開 ``` という多目的評価にする。 ただし全項目を固定重みにはせず、生成の進行に応じて重みを変化させる。 序盤： 「自然さ」「DNA」「テーマ」 中盤： 「展開」「変奏」「意外性」 後半： 「クライマックス」「緊張」「解放」「独創性」 というように進化させる。 ### 16. 「安全な美しさ」と「未知の美しさ」のバランスを時間とともに変える 生成開始直後は比較的保守的にする。 時間経過： ORIGIN → DISCOVERY → MEMORY → EXPANSION → DIALOGUE → TRANSFORMATION → COMPLEXITY → CRISIS → COLLAPSE → REBIRTH → OPEN WORLD という既存の進化構造を活用する。 序盤では音楽的安定性を優先し、中盤から徐々に探索範囲を拡大し、危機・崩壊では既存のルールを一時的に破壊し、その後のREBIRTHで過去の記憶と新しい発見を再統合する。 最終的には、生成時間が長くなるほど単純に複雑になるのではなく、 **安定 → 発展 → 混乱 → 崩壊 → 再発見 → 新しい安定** という音楽的生命サイクルを形成する。 ### 17. 重要：ランダム性を増やすだけの改修は禁止 「もっとランダムにする」 「音を大量に増やす」 「コード進行をランダム化する」 だけでは問題を解決しない。 必要なのは、 **生成 → 評価 → 記憶 → 変奏 → 交配 → 再評価 → 発見** という閉じた進化システム。 乱数は探索のために使い、最終的な採用は必ず音楽的評価を通す。 ### 18. 既存機能との統合 現在実装されている、 ・`scoreSegment()` ・`motifFit()` ・`newMotif()` ・`mutateMotif()` ・`xform()` ・`freshTheme()` ・`renewTheme()` ・`discoverTheme()` ・`evoScore()` ・`evoStep()` ・`evoVoices()` ・テーマmemory ・rhythm memory ・harmonic memory ・climax memory ・key memory ・tempo memory などを可能な限り活用し、同じ機能を重複実装しない。 特に現在の`scoreSegment()`は音程方向、跳躍、音域、ジグザグ、ラン、最高点などを評価しているため、これを破棄するのではなく、**新しい期待値・記憶性・フレーズ構造・緊張解放評価の基礎層として拡張する。** ### 19. 音楽的に最も重要な思想 このシステムの目的は、 「ランダムな音から美しい音列を作る」 ことではない。 目的は、 **「コンピューター自身が、何度も失敗し、記憶し、変奏し、忘れ、再発見しながら、自分が以前に作った旋律を材料として、より魅力的な旋律を発見していく」** こと。 人間の作曲家のように最初から完成品を出すのではなく、 「これは悪い」 「これは普通」 「これは面白い」 「これは変だけど残しておこう」 「以前のテーマと組み合わせてみよう」 「この4音だけは良い」 「この部分を新しいテーマにしてみよう」 という探索過程をアルゴリズムとして再現する。 最終的に目指すのは、**人間が最初に5音を与えた後、コンピューターがその5音から予想もしなかった美しいメロディを自律的に発見すること。** ### 20. 実装上の絶対条件 ・外部AI APIを使用しない ・外部音楽生成APIを使用しない ・インターネット接続不要で動作する ・単一HTMLで完結させる ・既存のオーディオシステムを壊さない ・既存の鍵盤入力を維持する ・既存のリアルタイム生成を維持する ・ブラウザ上で実用的なCPU負荷に収める ・無限生成を停止させない ・長時間生成してもメモリリークを起こさない ・生成履歴を適切に圧縮する ・同じ旋律ばかり生成しない ・単なる音の羅列に戻さない ・既存UIを壊さない ・コードを一から作り直すのではなく、現在の実装を解析して段階的に改良する そして改修後は、単にコードを追加するだけでなく、**実際に生成ロジックを検証し、明らかに「音の羅列」になっている箇所があればfitness・生成規則・フレーズ構造を再調整する。** 最終目標は「音楽理論的に正しいプログラム」ではない。 **人間が実際に聴いたときに、「これは単なるランダム生成ではない」「このメロディには何かがある」と感じること。** そのために、音符単位ではなく、**モチーフ → フレーズ → セクション → 全体という複数スケールで旋律を評価・進化させること。**
